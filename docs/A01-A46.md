### Дефекты, найденные при проверке A29

Критерий был отмечен выполненным без фактической проверки. Регрессионные тесты
обнаружили три ошибки, из-за которых распределение платежа не работало:

1. **`allocations` не было в Zod-схеме** маршрута — валидатор вырезал поле, и
   сервисный код был недостижим из API.
2. **Глобальный `prisma` внутри транзакции** в `applyPaymentAllocations` — тот же
   дефект взаимоблокировки, что был исправлен в `commercial.ts`; при
   `connection_limit=1` он приводит к таймауту.
3. **Деньги терялись молча:** платёж 120 000 распределялся как 70 000 + 0 при
   ответе `200 OK`. Причина — счета создаются только для заявки из заголовка.
   В ответ добавлено поле `unallocated`.
4. **Остаток в аудите считался неверно** (`payment - budget - (budget - left)`)
   и записывался отрицательным при каждом зачёте.
5. **Ручной зачёт обходил контроль переплаты:** платёж можно было распределить на
   сумму больше его собственной, распределяя по разным счетам. Автопуть такую
   переплату отклоняет.
6. **`paymentId` не возвращался** ни в одном маршруте, поэтому ручной зачёт был
   недостижим из API.

### Дефекты, найденные при сверке контрактов фронтенда и API

Отдельный проход по всем 74 вызовам `http.*` frontend-кода с проверкой формы
живых ответов. Найдено 10 расхождений контракта и 1 мёртвый вызов; до этого
HTTP-тесты проходили, потому что сервер отвечал 200, а ломалась отрисовка.
Десятым оказалось создание заявки через форму — его нашёл уже браузерный сценарий
с изменением данных, а не этот проход.

| Место | Что заявлено во frontend | Что отдаёт API | Симптом |
| --- | --- | --- | --- |
| `types.ts` `Dashboard` | `tasks`, `payments`, `shipments` как массивы | счётчики-числа и объекты | рабочий стол падал на `data.tasks.today.map` |
| `applications.ts` `tags` | `string[]` | JSON-строка `"[]"` | карточка заявки падала на `data.tags.map` |
| `types.ts` `Fulfilment` | `ordered`/`shipped`/`remaining`, `totals`, `complete` | `orderQty`/`shippedQty`/`remainingQty`, `finance.*`, `isFullyShipped` | вкладка «Исполнение заказа» падала на `totals.invoiced`, таблица оставалась пустой, бейдж всегда «есть остаток» |
| `types.ts` `CloseCheck.closingDocuments` | `{ required, registered }` | сводка в `summary`, на верхнем уровне поля нет | блок «Комплект: N из M» не выводился никогда |
| `AdminUsersPage.tsx` | `AdminUser[]` | `{ items, total, page, size }` | страница пользователей падала на `users.data.map` |
| `AdminReferencesPage.tsx` | `{ items: ReferenceItem[] }` | массив | страница справочников падала на `data.items.map` |
| `MailPage.tsx` | — | — | удалён мёртвый `GET /mail/inbox`, результат не использовался |
| `NewApplicationPage.tsx` | `POST /applications` как `ApplicationListItem` | конверт `{ application, deduplicated }` | форма уводила на `/applications/undefined`; заявка создавалась, но карточка не открывалась |

Проверено и оказалось корректным: `ApplicationDetail` на 100 заявках (56 полей
без расхождений; в ответе есть только 3 добавленных поля), `ReleaseCheck`
(в т. ч. snake_case `can_release_to_production`), `MyWork`, `Dashboard`
(все вложенные поля), `PlanFact`. Пять полей, которые API хранит как JSON-строку
(`audit.afterJson`, `imports[].mapping`, `imports[].rows`, `outbox[].payload`,
`engineering[].inputSnapshot`), фронтенд не трактует как массивы, поэтому
приводить их в ответе к массивам незачем; типы объявлены как строки.

Ответы мутаций, которые используются без перезагрузки, сверены отдельно.
`LoginResponse` (4 поля) и `ImportCommitResult` (`batch`, `created`, `failed`)
совпадают с объявленными типами. `POST /applications` при первом проходе был
оценён как безопасный: ответ формально «шире» объявленного типа, лишние поля
казались безобидными. Это была ошибка вывода — ответ устроен иначе: `number`
лежит внутри `application`, а на верхнем уровне его просто нет. Нашёл баг
браузерный сценарий, а не этот проход.

Второй проход по вложенным полям нашёл ещё одно расхождение — в `/pipeline`:

| Место | Что заявлено | Что отдаёт API | Симптом |
| --- | --- | --- | --- |
| `Pipeline.totals` | `applications` | `created`/`active`/`won`/`lost`, `conversionToContract`, `conversionToWon` | «Заявок в периоде» всегда показывало 0 |
| `Pipeline.stageDurations[]` | `avgDays` | `samples`, `medianHours`, `maxHours` | сроки этапов пустые, полоса получала `width: NaN%` |
| `Pipeline.openQuotes` | `{ count, amountByCurrency }` | сумма по валютам | карточка не отображалась вовсе |

`AnalyticsPage` переведён на фактические поля: длительности пересчитываются из
часов в дни, добавлены конверсия в договор и в выигрыш, сумма открытых КП по
валютам. Новые 4 проверки в `smoke.ts`.

Проверка живой отрисовки закреплена как постоянный скрипт
`frontend/scripts/ui-check.mjs` (`npm run ui:check`, каталог `frontend`). Он
открывает 14 маршрутов, включая форму входа без токена и форму новой заявки, и
все вкладки карточки в headless Chrome через Chrome DevTools Protocol и падает с
ненулевым кодом возврата, если на экране есть необработанное исключение, блок
ошибки, неуспешный запрос API или не выполнено ожидаемое содержимое. Зависимостей
нет: CDP держится на встроенном в Node `WebSocket`, поэтому Playwright и Puppeteer
ставить не нужно. Скрипт сам подбирает заявку, у которой есть закрывающие
документы, — иначе вкладка исполнения оставалась бы пустой и не замечала бы
регрессию контракта. Общий слой браузера вынесен в `scripts/lib/browser.mjs` и
обслуживает оба скрипта.

Скрипт проверен на способность ловить дефекты: с возвращённым багом
`closingDocuments?.items` вкладка «Исполнение и закрытие» падает, при этом
контракт HTTP-тесты не видят, потому что ответ API корректен. Текущий прогон —
24 экрана и 30 содержательных проверок, дефектов 0.

Три ошибки самого скрипта, найденные при переносе, важны для понимания, почему
ему нельзя доверять без проверки:

- `child.kill()` не убивает дерево процессов Chrome, порт отладки остаётся
  занят, и следующий запуск подключался к браузеру прошлого прогона, у которого
  в `localStorage` лежал токен. Проверка формы входа молча проверяла
  авторизованную страницу. Теперь порт выбирается свободным, а закрытие идёт
  через `Browser.close` и `taskkill /T`;
- `Log.entryAdded` не содержит URL в тексте ошибки, поэтому фильтр шума по
  `favicon` не мог сработать, а диагностика была слепой. URL добавлен в запись;
- ожидания выполнялись сразу после навигации, пока данные ещё не пришли: счётчик
  на рабочем столе то проходил, то нет. Теперь каждое ожидание опрашивается до
  четырёх секунд, а ошибка выражения больше не глотается — «упало» и «не выполнилось»
  больше не выглядят одинаково.

Чего проверка не ловит: если API отдаёт нулевые значения, подмена одного поля на
другое с тем же нулём неотличима от корректной отрисовки. В наборе данных
`medianHours` и `maxHours` равны нулю во всех шести этапах, поэтому чтение
`avgDays` вместо `medianHours` даёт ту же картинку. Такие вещи ловит проверка
контракта в `smoke.ts`, а не браузер. Поэтому проверки содержания написаны так,
чтобы требовать корректность (числа разбираются, ширина полосы в диапазоне
0..100 %, нет `NaN`), а не наличие ненулевых данных.

### Сценарии, которые меняют данные

Отдельный скрипт `frontend/scripts/ui-flows.mjs` (`npm run ui:flows`). Чтение
экранов не проверяет главное — что кнопка действительно работает. Сценарии
проходят действия по-настоящему: заполняют форму, нажимают кнопку, сверяют
результат на экране и через API.

1. Создание заявки через форму новой заявки: заполняются контрагент, контакты,
   вероятность, метки, комментарий, позиция с количеством и ценой; после отправки
   проверяется, что открылась карточка созданной заявки, и через API — название
   организации, разбор меток в массив и сохранённая позиция.
2. Задача через интерфейс: модальное окно, тема и срок, затем откат штатным
   действием `POST /tasks/:id/cancel` и проверка статуса `CANCELLED`.

**Найденный баг.** Создание заявки через интерфейс было сломано полностью:
`POST /applications` возвращает конверт `{ application, deduplicated }`, а форма
читала `result.number`, который всегда `undefined`, и уходила на
`/applications/undefined`. Пользователь, заполнивший форму, попадал на
несуществующую страницу, а созданная заявка оставалась без открытой карточки.
Тип в TypeScript при этом объявлялся как `ApplicationListItem`, поэтому компилятор
и все HTTP-тесты были довольны: `smoke.ts` читает `application.number` правильно.
Исправлено в `NewApplicationPage.tsx`; заодно убран неверный тип ответа в
`MailPage.tsx`, где результат и не использовался. На это указывает только
браузерный сценарий — HTTP-тесты такой баг увидеть не могут.

Откат данных: заявку удалить нельзя, `DELETE /applications/:number` в API не
предусмотрен, поэтому уборкой занимается maintenance-скрипт
`backend/scripts/cleanup-test-applications.ts` (`npm run test:cleanup`). Он идёт
в базу напрямую через Prisma и трогает только организации, в названии которых
есть маркер `UI-CHECK`, то есть исключительно то, что создал `ui:flows`.
Заявку нельзя снести одной командой: пять связей объявлены в схеме без
`onDelete: Cascade` (`engineeringConclusion`, `mailMessage`, `auditEvent`,
`integrationLink`, `outboxMessage`), и без их удаления падает внешний ключ;
остальные девять таблиц схема сносит каскадом. Перед удалением выводится
список того, что будет стёрто, `--dry-run` ничего не меняет, повторный запуск на
чистой базе безвреден.

Поведение по итогам прогона:

- все сценарии прошли — заявка, контакт и организация удаляются автоматически,
  и после прогона в базе не остаётся следов;
- сценарий провалился — чистка не выполняется, данные остаются как улика, а в
  выводе печатается команда для удаления;
- `npm run ui:flows -- --keep` — оставить заявку для разбора, не чистить.

### A46: логотип

Официальный логотип взят с сайта https://uniprom.pro/ и положен в
`frontend/public/brand/`:

| Файл | Назначение | Особенность |
| --- | --- | --- |
| `logo.svg` | знак «У» для квадратной плитки (сайдбар) | градиентный, не зависит от фона |
| `logo-lockup.svg` | знак с надписью для светлого фона (страница входа) | надпись `#0B1220` |
| `logo-lockup-on-dark.svg` | знак с надписью для тёмного фона | надпись белая, как на сайте |

Палитра приведена к фактическому градиенту знака (`#1BC4ED` → `#1189F4` →
`#0445FB`) в `frontend/src/brand.ts` и `frontend/src/styles.css`, вместо ранее
выбранных `#1c5cff` / `#376ffc`, которые логотипу не соответствовали.

Версия с сайта рассчитана на тёмную шапку: надпись в исходнике залита белым. На
белой панели сайдбара она была бы не видна, поэтому сделана отдельная версия с
тёмной надписью; для тёмных поверхностей сохранён исходный вариант без
изменений.
